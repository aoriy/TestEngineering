## 一、可行性总评

| 维度 | 评级 | 说明 |
|------|------|------|
| 技术可行性 | **高** | 全部成熟技术，无未解难题 |
| 市场可行性（当商业产品） | **低** | Katalon / Tosca 已占位，画布差异化不值钱 |
| 可行性（当个人工具） | **高** | 解决真实痛点，不需要商业回报 |
| 工程可行性 | **中** | 取决于范围控制——核心差异化可行，全模块做重则险 |

### 核心判断

本项目的方案是 **MBT 状态机 + 页面对象仓库 + 数据流编排** 三者的图形化融合，商业市场上没有现成对标。但商业化前景低（Katalon / Tosca 已占位且画布差异化收益不显著）；作为**个人工具**可行（解决测试员自己的痛点，无需商业 ROI 论证）。

**收缩范围、聚焦差异化**是可行性的关键。

## 二、技术可行性（高）

### 2.1 全部技术成熟

| 技术点 | 成熟度 | 证据 |
|--------|--------|------|
| 录制回放 | 成熟 20 年 | Selenium IDE（2004）、Playwright codegen |
| 可视化画布拖拽 | 成熟 | AntV X6（国内大量项目用）、LogicFlow |
| 步骤 / 对象可视化组织 | 有先例 | Katalon 对象仓库、RobotFramework RIDE（1,011 stars） |
| 页面元素定位 | 成熟 | Playwright、data-testid 规范 |
| 代码相 | 成熟 | Monaco Editor（VSCode 同款） |
| 变量模板 | 成熟 | Jinja2（`{{var}}` 天然支持） |
| API 响应提取 | 成熟 | jsonpath-ng、正则、XPATH |
| Locust 性能 | 成熟 | Python 原生，分布式 |
| OpenAI 兼容协议 LLM | 成熟 | DeepSeek / Qwen / GLM 均兼容 |
| 一份模型多执行 | 有先例 | Tricentis Tosca 的 model-based approach |
| LLM 驱动测试用例 | 已落地 | HttpRunner v5（4295 stars）已用 LLM 驱动用例 + MCP server |

**结论**：无任何未解技术难题。所有组件都有生产级实现。

### 2.2 关键技术成熟度细分

#### 录制回放执行核心
- 完全可行。Playwright codegen 现成，可录制操作 + 定位器自动生成步骤
- 这是市场 20 年验证过的路，本项目定会走通的根基

#### 画布式元素组织
- AntV X6 支持形状 + 端口 + 连线 + 双击弹代码面板，全部现成
- 工程量在语义设计，不在画图本身

#### 代码钩子运行
- 把 Python 代码字符串 exec 在受控上下文中（传入 `ctx` 对象）
- 安全性需要约束（限制 import、超时控制），但单人使用风险可控

#### AI 自愈
- OpenAI 兼容协议 + DeepSeek 已实证可达（`deepseek-v4-pro` + thinking mode，OpenAI 兼容 `client.chat.completions.create`）
- 复杂度在 Prompt 工程和 HTML 截断策略，不在底层
- Testim 被 Tricentis 收购正是靠 AI Smart Locator 自愈 → 印证成熟
- **HttpRunner v5 已在用 LLM 驱动 UI 自动化（OCR/CV/VLM）**→ 进一步印证这条路在开源界已有投入
- **真正风险是误判而非成本**：三层防线（Playwright 验证 + 语义指纹校验 + 置信度门限）是核心投入

## 三、工程可行性（中，关键在范围控制）

### 3.1 单人交付的真实风险

四大模块全做重 = 一个商业公司多年积累。Katalon 有几十人团队。单人完成全部模块的风险点：

| 模块 | 单人做重风险 | 建议 |
|------|------------|------|
| 需求 + 用例管理 | 中 | 够用版 CRUD 即可，不做报表 / 审批 |
| 页面简图画布 | **高（核心）** | 投入主要精力，但警惕过度设计 |
| 代码钩子 + 变量 + 执行 | **高（核心）** | 必须做重，是差异化所在 |
| AI 自愈 | 中 | 用第三方 API 即可，不自研模型 |
| 性能（Locust） | 低 | 复用接口定义，给启动按钮即可 |

### 3.2 范围控制的原则

**收缩范围，把火力集中在差异化核心：**
- **重做**：页面简图画布 + 代码钩子 + 变量系统 + 录制导入 + 执行引擎 + AI 自愈
- **轻做**：接口测试（requests 直接跑）、性能（Locust 复用）
- **最轻**：需求管理、用例管理——先做够用的 CRUD + 追溯，不做花活

省下的时间全部投入阶段 2-3-3.5（画布 + 执行 + 自愈），这是独特点。

**为什么不借力 MeterSphere / HttpRunner**：HttpRunner v5（Go）虽覆盖一致，MeterSphere（Java）虽一站式，但栈都不同。借力的代价是用例在别处跑、画布在 Python 端——**割裂没解决反而强化了**。本项目"Python 全栈 + Web 画布"生态位在开源里暂无人占位，自研反而成了优势。后续可考虑兼容 HttpRunner 的 testcase 格式做导入导出。

### 3.3 推荐的里程碑裁剪

如果时间紧张，最小可行版本（MVP）甚至可以只做：
- **MVP 版本**：页面简图画布 + 步骤列表 + 定位器 + Playwright 执行（先不做代码钩子和变量联动）
- 再加 AI 自愈 → 已经超过 Katalon 免费版的核心体验
- 最后才补需求 / 用例 / 性能

## 四、市场可行性（当作商业产品：低）

### 4.1 竞争替代

Katalon 免费版 + 录制 + **AI 自愈**（页面变了自动修 XPath）已覆盖"测试员不想写代码"的诉求。
- 它的 AI 自愈是单人**原本做不出**的（市场调研时的判断）
- **本项目通过第三方 API key（DeepSeek）补上了这块** → 最大短板化解
- 但 Katalon 还有云执行、移动端、企业集成等单人短期达不到

### 4.2 画布差异化的真实价值

正如用户自己承认的："**简图只是让列表更直观而已**"。要诚实承认：
- 列表 / 树状对 99% 的用例足够直观，画布是"第 100 个复杂用例才爽"的功能
- 画布的收益是小众的，但成本（拖拽、排版、连线）由**每一个用户**承担
- 商业产品算过账：不值得。但这不等于"不可行"，只是"不值当卖钱"

### 4.3 目标用户窄

- 图形化建模的服务对象是"不会写代码的测试员"，但恰恰是这批人维护模型更吃力
- 会写代码的工程师 → 直接写 Playwright 更高效
- **"会写代码但又想用图形"的中间人群太小**

**结论**：作为商业产品，画布差异化撑不起付费意愿。**作为个人工具不必纠结这个**。

## 五、作为个人工具的可行性（高）

### 5.1 核心优势：你自己就是用户

- 不需要商业 ROI 论证——只要"画布 + 代码钩子 + 变量联动"让你的用例比纯脚本直观、好维护，就是成功的
- 市场要卖给所有人，你只要自己好用
- 这意味着"太小众不值得卖"对你是无关的约束

### 5.2 解决真实痛点

| 痛点 | 本项目解法 | 个人收益 |
|------|----------|---------|
| 列表不直观 | 页面简图画布 | 提升理解效率 |
| UI / API 割裂 | 一份模型双执行 | 减少重复维护 |
| 关联字段联动 | 接口返回值驱动 | 复用难复用逻辑 |
| 定位器失效 | AI 自愈 | 减少手动修定位器 |

### 5.3 技术栈与现有经验对齐

- 后端 FastAPI（兄弟项目 `fastAPI` / `flask_test` 经验）
- 前端 Vue3 + AntV X6（国内生态好）
- 执行 Playwright（兄弟项目 `playwright_demo` / `python_test_ui` 经验）
- AI openai 库（兄弟项目 `python_test` 已用，配置约定可沿用）
- 一切都在熟悉栈内，无学习成本陡坡

## 六、风险点与对策

### 6.1 风险一：范围失控

**风险**：四大模块全做重，单人无法完成，半途而废。
**对策**：阶段计划体现范围控制；阶段 1 大幅削减；**先做 MVP（画布 + 执行）再补外围**。

### 6.2 风险二：定位器维护负担

**风险**：虽然简图不需要跟页面强相关，但元素定位器页面改了还是得重新录。
**对策**：
1. AI 自愈（DeepSeek 适配器，验证后自动修复）——化解 80%
2. data-testid 优先策略——根源降低失效概率
3. 自愈审计可回滚——保安全

### 6.3 风险三：简图维护成本与 Katalon 等的差距

**风险**：Katalon 的 AI 自愈是闭源自研模型，本项目的 DeepSeek 适配器效果不一定赶上。
**对策**：
- 采用"HTML 截断 + Prompt 优化"控制效果与成本
- 保留手动修兜底
- 不追求赶上 Katalon，只要比纯脚本省力

### 6.4 风险四：代码钩子的安全性

**风险**：用户在形状上写 Python 代码，运行时 exec 可能不安全。
**对策**：
- 单人工具风险可控
- 限制可用 import 白名单
- 超时控制
- 沙箱运行（后续可加）

### 6.5 风险五：动态页面状态难建模

**风险**：弹窗、iframe、异步加载 — 简图是静态的画不出动态行为。
**对策**：
- 代码钩子是逃生舱，画不出的用 Python 兜
- 设计"等待"和"条件"形状节点覆盖常见动态场景
- 不强求 100% 图形化

## 七、推荐方案与结论

### 7.1 推荐方案

**收缩范围 + 聚焦差异化 + AI 自愈补短板**：

1. 核心投入：**页面简图画布 + 代码钩子 + 变量系统 + 录制导入 + 执行引擎**
2. 借力 AI：**DeepSeek 适配器自愈 + 报告 / 用例建议**
3. 外围轻做：需求 / 用例够用 CRUD，Locust 复用接口

### 7.2 可行性结论

- **技术上完全可行**：所有组件成熟，无未解难题
- **市场定位清晰**：不作商业产品，作为个人工具解决真实痛点
- **工程可行在范围控制**：阶段 1 削减，重兵在阶段 2-3-3.5
- **AI 自愈补上最大短板**：原本是单人做不出来，现通过第三方 API 化解
- **避开 MBT 死路**：简图定位为"组织层"不绑定页面，避开模型漂移

### 7.3 给用户的最终建议

1. **接受个人工具定位**：别纠结商业化 ROI
2. **先做 MVP 再扩**：画布 + 执行跑通，再考虑外围模块
3. **AI 自愈必做**：通过 DeepSeek 补齐核心短板
4. **保持"简图是组织层"的纪律**：不要逐步滑向"页面建模"，否则撞上 Spec Explorer 死路
5. **范围上限守死**：需求 / 用例 / 性能模块只做够用，不碰花活

## 九、第二轮实证深挖补充（开放问题收敛）

经第二轮实证调研（代理已通，DeepSeek / HttpRunner / Allure 实测确认），6 个开放问题全部收敛，详见 `requirements-analysis.md` 第十章。要点：

5. **接口用例形态**：数据流走画布 + 顺序走列表，共享 ApiDefinition
6. **报告**：MVP 用 pytest-html，Allure 可选开关
